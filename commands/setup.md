---
description: First-run hits setup — install the binaries, connect through a chronicle context or a hits context with an actor, select an initiative, verify with ping and a read
argument-hint: "[context name]"
---

Walk the user through getting hits working end to end. Fix each step before moving to the next; finish by reporting what is configured and what (if anything) still needs a restart.

1. **Binaries.** Run `hits version`. If missing, or older than 0.10.0 — the first client that serves both a HITS on chronicle and a 0.7 fleet — install: `brew install impire-io/tap/hits` (installs `hits` and `hits-mcp` together), a release archive from https://github.com/impire-io/hits/releases, or `go install github.com/impire-io/hits/cmd/hits@latest` plus `.../cmd/hits-mcp@latest`. A chronicle context needs chronicle's own CLI as well: `brew install impire-io/tap/chronicle`.
2. **Context.** The connection is a saved context, and the context chooses the substrate. Ask which HITS the user reaches, then take the one route:
   - **A HITS on chronicle** — the usual route: a chronicle context, saved by chronicle's own CLI, never by hits. `chronicle context list`. If none fits: a person signs in to the hosted account with `chronicle login`; a credential on a NATS the user runs is saved with `chronicle context add`. Make it the selection with `chronicle context select <name>`.
   - **A HITS of release 0.7.0** — a fleet an operator still runs, frozen at that release: a hits context. `hits context ls`. If none fits: `hits context add <name>` creates one, `hits context import <name>` brings a nats CLI context over. Make it hits's default with `hits context select <name>`. If the context carries an `oauth` block, run `hits auth login --context <name>` (device flow — show the user the URL and the code) and confirm with `hits auth status`.
   If the user named one in $ARGUMENTS, target that. A name resolves against chronicle's contexts first, then hits's own; a name both families hold is refused — rename one. With no name, `hits` and `hits-mcp` use chronicle's selection, else hits's default.
3. **Author.** On a chronicle context: nothing to set. Every write's author is the context's principal — the user's GitHub login on the hosted account, a service account's name for an agent — vouched for by chronicle, and `--actor` or `HITS_ACTOR` is refused. An agent that must write as itself needs its own service account and its own context, not the user's. On a hits context: every write needs a stable lowercase handle. Ask the user for theirs and set it as `defaults.actor` in the hits config (`~/.config/hits/config.json`, as 0.7 had it) — the one place both the CLI and `hits-mcp` pick it up without a per-command flag; `HITS_ACTOR` in the environment does the same.
4. **Store and initiative.** `hits initiative list`. On a chronicle context, if it says the store or its types do not exist, the account has no HITS yet: an admin of the account runs `hits store init` once (every step idempotent; a chronicle-only verb — a fleet is not declared, it runs). Then, on either substrate: filing mints item IDs from an initiative — the group of projects the user works in. If theirs is listed, `hits initiative select <slug>`; if the install has none yet, register it first (`hits initiative register <slug> <name>`). The selection lands in hits's own config file — a filing default, never a read scope.
5. **Verify.** `hits ping` names what answered — the store's announcement on chronicle, the node's name and version on a fleet. Then `hits get <id>` on any known item, or `hits search` with a word. A failure on a chronicle context is the context's — fix it with chronicle's CLI (`chronicle context show`). `unreachable` on a hits context means no fleet is running there: this client starts nothing, and the fleet is its operator's to run from the 0.7.0 release's own binaries.
6. **MCP server.** If the hits MCP tools are not present in this session, the server was not connected at startup — now that a context is selected, reconnect it (`/mcp`) or restart Claude Code. On a hits context the server needs the actor at startup: `HITS_ACTOR` in the environment, which the plugin's launcher passes through, or the hits config's default; on a chronicle context it takes none and refuses one. A host running several agents runs one server per agent, each on its own context.
